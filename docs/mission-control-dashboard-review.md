# TrueNAS Mission Control Dashboard Review

Review date: 2026-07-14

Independent second pass: 2026-07-14

## Scope

This review covers the rendered screenshots in `grafana-dashboard/screenshots/`
and the generated dashboard resource in
`grafana-dashboard/truenas-mission-control.json`.

The dashboard is a Grafana App Platform resource:

- `apiVersion`: `dashboard.grafana.app/v2beta1`
- `kind`: `Dashboard`
- `metadata.name`: `truenas-mission-control`
- layout: native `TabsLayout`
- panels: 312 v2 panel elements
- tabs: 12
- variables: 11

`truenas-mission-control.json` is generated by
`grafana-dashboard/build_mission_control.py`. Future changes should be made in
the builder and, where query behavior comes from the classic dashboard, in
`grafana-dashboard/operations-center-dashboard.json` before regenerating.

## What Works Well

The dashboard has a strong operational shape. The tab structure matches how a
TrueNAS operator thinks: overview first, then compute, storage, datasets, disks,
network, sharing protocols, apps, virtualization, alerts, security, and exporter
health.

The overview makes a good first impression. The first viewport shows system
readiness, alert count, pool health, capacity pressure, CPU, RAM, disk
temperature, update state, scrape time, and core trends. For a live wallboard or
demo, this is visually strong and quickly communicates that the dashboard is
not just a raw metric dump.

Storage is one of the strongest areas. Pools, ZFS health, ARC behavior, pool
capacity, fragmentation, scan progress, inventory, and dataset capacity are
grouped in ways that support real troubleshooting.

The dashboard preserves portability by using a Prometheus datasource variable
and regex matchers for the multi-value `$instance` variable. All 406 Prometheus
panel queries use `instance=~"$instance"` rather than an exact matcher, so the
`All` selection is handled correctly.

The generated v2 structure is clean. There are no orphan elements, missing
references, duplicate panel IDs, or grid overflow issues.

## Main Issues

### 1. The dashboard is too dense for one operator workflow

The dashboard has 312 panels. The largest tabs are:

| Tab | Panel references |
| --- | ---: |
| Exporter & Config | 45 |
| Security & Audit | 40 |
| Overview | 39 total / 19 default-visible |
| Shares & Protocols | 37 |
| Pools & ZFS | 27 |
| Apps & Docker | 27 |
| Alerts & Jobs | 25 |

This is impressive as a metric-surface showcase, but it is heavy for incident
response. The Overview's 39 references include 20 inventory panels that are
already in the collapsed `System Snapshot` row, so describing all 39 as
competing in the default view overstates the problem. The 19 visible hero
panels still exceed the usual eight-panel Overview budget. The first viewport
works reasonably well as a 30-second scan, but per-core CPU series and secondary
trends compete with the most urgent signals.

Recommended change: keep Mission Control as the broad showcase, but make the
landing tab stricter. Limit the top overview to the few signals that answer:
system up, active critical/warning alerts, pool capacity, pool health, boot
health, API scrape health, update/reboot risk, and one resource trend. Move
any remaining secondary inventory into the existing collapsed `System
Snapshot` row or a separate inventory tab.

### 2. Red/yellow/green semantics are inconsistent

Several panels use strong red for `No` values where the meaning is not always
obvious:

- `Security & Audit`: `2FA`, `FIPS`, `Production`, `iX Hardware`,
  `Support A+E`, `Security FIPS`, `GPOS STIG`, `FIPS Avail`.
- `VMs & Virt`: `Intel VMX`, `Unrestricted`, `Virt Error`.
- `Network`: `Pending Changes`.
- `Alerts & Jobs`: `Reboot Req`.
- `Exporter & Config`: `Reporting On`.
- `Disks & Hardware`: `ECC Memory`, `Resilver On`.
- `Shares & Protocols`: `SMB1`, `NTLMv1`, `NFS RDMA`, `ALUA`, `iSER`, and
  disabled services.
- `Security & Audit`: `FTP`, `SNMP`, `Dir Svc Cfg`, `Dir Svc OK`, and `Remote
  Log` in addition to the policy-dependent controls above.
- `Exporter & Config`: inactive boot environments and flags are rendered as
  red `Down`/`No`, although only one environment is expected to be active.

There are also definite inversions rather than merely contextual mappings:

- The Overview hero renders `update_available=0` as green `Up to date`, while
  the expanded `System Snapshot` renders the same value as red `No`.
- `App Inventory` renders `upgrade_available=1` and
  `image_updates_available=1` as green `Yes`, while `0` is red `No`.
- `Running Job Progress` changes from green to yellow at 50% and red at 90%,
  even though approaching completion is not inherently unhealthy.

Some of these are clearly bad, some are contextual, and some are normal for a
given host. Treating all of them as critical red creates alert fatigue and makes
the genuinely urgent panels less trustworthy.

Recommended change: split boolean mappings into explicit categories:

- security finding: red/yellow/green with clear action text
- unsupported/not installed: neutral gray/blue
- absent and healthy: green only when absence is actually good
- unknown/no data: gray or yellow, never green

Examples:

- `2FA`: red `Disabled`, green `Enabled`.
- `FIPS`: neutral `Off` unless this deployment requires FIPS.
- `ECC Memory`: neutral `Not reported` if the hardware/API does not expose it;
  red only if ECC is expected and absent.
- `Pending Changes`: green `None` is clearer than red `No`.
- `Reboot Req`: green `No reboot required`, red `Reboot required`.

### 3. No-data states are sometimes shown as healthy

Screenshots show several panels where missing data is visually green or takes
up high-value layout space:

- `Disks & Hardware`: `Avg Busy` shows green `No data`.
- `Alerts & Jobs`: `Critical` shows green `No data`.
- `Pools & ZFS`: `Pool Expansion Progress` and `Pool Realtime I/O` show no
  data in prominent positions.
- `VMs & Virt`: Incus CPU and memory panels show no data on a host with no VMs.
- `Security & Audit`: `Certificate Expiry` shows no data.
- `Network`: `Checkin Wait` is empty.
- `Datasets`: `Dataset Snapshot Counts` and `Datasets with Reservations` are
  empty half-width panels in the default tab layout.
- `Disks & Hardware`: several IPMI state tiles are blank but retain green
  backgrounds, and a disk with an unavailable temperature appears as green
  `0 C`.

Recommended change: use explicit no-data mappings and move expected-empty
panels into collapsed or lower-priority sections. A panel that is empty because
the feature is not configured should say that, for example `No Incus
instances`, `No pool expansion running`, or `No certificates reported`.

### 4. Some panels look like transform or alias issues

There are visible labels that look generated rather than operator-facing:

- `Alerts & Jobs`: `Tasks by Type` repeats metric/label fragments instead of
  concise task type names.
- `Alerts & Jobs`: `Alert Classes` shows repeated `Value klass` labels.
- `Exporter & Config`: `API Method Success` is so dense that method names
  overlap and the panel becomes unreadable.
- `Disks & Hardware`: `Disk Sizes` shows metric-name-like labels instead of
  clean disk names.
- Dataset bar gauges show long full paths that are hard to scan.
- `Network` and `Shares & Protocols`: interface, service, and SMB state
  timelines display `-oo+`-style values rather than their configured
  `Up`/`Down` or encryption-mode labels.

Recommended change: tighten transformations and legend/display names. Use
short labels for charts and keep full identifiers in table columns or data
links. For dense state timelines, show top failing methods only, or move the
full per-method view to a table sorted by errors/duration.

### 5. A few units and titles can mislead

Most bytes, percentages, durations, and temperatures are correctly formatted,
but many panels still use the generic `short` unit. That is fine for counts,
but not for operational states or settings where a custom mapping would be
clearer.

Specific examples:

- `Disk Busy %` reached nearly 300% while the documented metric range is
  0-100%. The visible series is `disk="total"`, not an individual disk.
- `NTP Min Poll` and `NTP Max Poll` are already exported in minutes, not as raw
  poll exponents. Their `short` unit drops that context; use an explicit minute
  unit or include `(minutes)` in the title.
- `Interface MTU` renders `1500` as `1.50 K`; use an unscaled numeric or byte
  presentation appropriate for an MTU.
- `HTTPS Port` should stay numeric, but it is configuration, not health. It
  should not compete visually with fault panels.
- `Documented Memory Capacity Over Time` reads like documentation metadata.
  `Memory Capacity Over Time` is clearer.
- `Oldest Alert Age` showing `50.2 weeks` in the exporter tab is surprising
  and needs context. If it includes historical/dismissed alerts, say that in
  the title or description.

Recommended change: audit the 177 panels using `short`. Keep it for true counts
only. Use mappings for booleans/states, seconds for intervals, bytes for sizes,
percent/percentunit for ratios, and explicit wording for configuration values.

### 6. Exporter health queries can misstate current health

`API Success %` is calculated as `100 * avg(truenas_api_call_success)`. The
metric is a per-method gauge that reports whether the latest scrape call
succeeded, so the panel is the percentage of methods whose latest call
succeeded, not an API call success rate.

`API Errors` and `Coll Errors` display raw counters accumulated since exporter
start and apply fixed red thresholds to their lifetime totals. The same raw
collector-error counter is also graphed in `Exporter & Event Stream Health`.
These panels can remain red long after recovery and do not communicate current
error rate.

Recommended change: rename the success panel to describe latest-scrape method
health, and show `rate()`/`increase()` for current errors while retaining
lifetime totals only when clearly titled `since exporter start`.

### 7. Screenshots reveal exporter/data-quality problems

Some screenshot anomalies cannot be resolved only through layout changes:

- `Disk Throughput by Device`, `Disk IOPS by Device`, and `Disk Busy %` admit
  the synthetic `disk="total"` series. The screenshots show only `total` for
  these panels. `Avg Busy` excludes `total` and consequently shows no data,
  indicating that usable per-device busy data was not present in this capture.
- `Disk Busy %` reaches 296% despite its metric contract stating 0-100%.
- `Pool Scan Progress` reaches 101% despite its metric contract stating 0-100%.
- Disk `sde` reports 0 C and is colored healthy, which likely represents an
  unavailable sensor encoded as a valid value.
- `Oldest Snap` shows `n/a` while the dashboard reports 16 snapshots, which
  warrants checking timestamp collection and zero/NaN handling.

Recommended change: verify exporter normalization and fixture coverage first.
Then exclude or explicitly label aggregate disk series in per-device panels,
and map unavailable sensor values to no-data rather than healthy zero.

### 8. CPU and method panels have too much legend pressure

The Compute tab shows both `CPU Usage` and `Per-Core CPU Usage`, which appear
duplicative in the screenshots. Each per-core panel has many series and a
legend that consumes substantial vertical space.

The same pattern appears in exporter method duration/success panels. They
contain useful data, but the series count is too high for a dashboard panel.

Recommended change: keep one high-level CPU trend in the default Compute view
and make per-core detail collapsible or drill-down only. For API methods, show
top slow methods and top failing methods, then use a table for the complete
method list.

### 9. Alerts and jobs need stronger action hierarchy

The Alerts & Jobs tab contains the right information, but it should be more
action-oriented. Current high-value panels include total alerts, warning count,
alert sources, active jobs, job progress, and alert count over time. However,
less important stats such as dismissed/one-shot/transient counts sit near the
top, and some active job panels are below noisier distributions.

Recommended change: order the tab around response workflow:

1. Critical/warning active alerts and reboot/update risk.
2. Alert source/class table with clean labels.
3. Active jobs and riskiest job progress.
4. Alert count trend.
5. Scheduled task inventory and dismissed/transient detail.

### 10. Security needs policy context

The Security & Audit tab is useful, but policy-dependent checks need context.
For example, FIPS, STIG, production mode, directory services, remote logging,
and support access are not universally required. Red should mean "this violates
the intended policy", not just "the value is false".

Recommended change: add policy-aware descriptions and, if practical, variables
or dashboard variants for home-lab, small-business, and regulated deployments.
Without that, use neutral styling for optional controls and reserve red for
clear risks such as 2FA disabled, directory service down when configured,
certificate expiry, audit storage pressure, or active security faults.

### 11. Query and variable choices are mostly safe, with refinements

The panel queries are well scoped to `$instance` and use regex matchers for the
multi-value variables. All 406 Prometheus panel queries use the expected
`instance=~"$instance"` matcher, and no exact matchers were found for the other
multi-value panel variables. The app block I/O panels use `$__rate_interval`,
which is the right Grafana pattern. `Event Messages Rate` still uses a fixed
`[5m]` window; it is safe for the current cadence but should be reviewed for
consistency with the adaptive rate-window policy.

The dashboard variables are already schema-v2 `DataQuery` wrappers, but their
query bodies use classic Prometheus `label_values(...)` text. Moving to the
newer structured Prometheus variable-query fields is therefore a minor cleanup,
not a missing schema-v2 conversion. The `$method` variable also exposes a large
method set that directly contributes to unreadable API panels.

## Recommended Work Plan

### Priority 0: Fix misleading states

- Add explicit no-data mappings for expected-empty panels.
- Stop rendering no-data as green health.
- Reclassify red `No` mappings into policy failure, unsupported, absent-good,
  and unknown categories.
- Fix the contradictory Overview update mappings, inverted app-update table
  mappings, and job-progress thresholds.
- Fix visible transform/alias issues in `Alert Classes`, `Tasks by Type`,
  `Disk Sizes`, state timelines, and `API Method Success`.
- Correct the API success/error semantics and investigate the out-of-contract
  disk, pool-progress, temperature, and oldest-snapshot values.

### Priority 1: Improve layout hierarchy

- Reduce the Overview tab to a true 30-second health check.
- Keep inventory counts and low-action settings in the existing collapsed
  Overview row or move them to lower-priority tabs.
- Collapse or split the largest tabs, especially Exporter & Config, Security &
  Audit, and Shares & Protocols.
- Make dense detail panels drill-down/table-oriented rather than always visible.

### Priority 2: Improve polish and maintainability

- Audit generic `short` units and replace them with state mappings or concrete
  units where appropriate.
- Shorten chart labels and move full paths/method names to tables or links.
- Add descriptions to the remaining panels without descriptions, especially
  boolean/status panels where policy context matters.
- Consider structured Prometheus variable queries in the v2 dashboard builder.
- Replace the fixed event-message rate window if adaptive behavior is desired.
- Add dashboard links or panel links from overview alert tiles to the relevant
  tab/row with time and variables preserved.

## Bottom Line

Mission Control is a strong showcase dashboard and a good broad operational
surface. Its biggest problem is not missing coverage; it has the opposite
problem. It should now be refined for operator trust: fewer competing signals
on the landing page, stricter severity semantics, clearer no-data handling,
cleaner labels, accurate query semantics, and more drill-down structure for
dense panels. Several disk, pool-progress, temperature, and snapshot anomalies
also require exporter/data-quality investigation rather than dashboard-only
polish.
